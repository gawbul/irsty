# Packaging and releases

Irsty is released as archives on GitHub, built by [dist](https://opensource.axo.dev/cargo-dist/), and as crates on [crates.io](https://crates.io/crates/irsty), so `cargo install irsty` works. The project site is built from these docs by mdBook and deployed to GitHub Pages.

## What a release contains

For each of `aarch64-apple-darwin`, `x86_64-apple-darwin`, `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu` and `x86_64-pc-windows-msvc`, an archive (`.tar.xz`, or `.zip` on Windows) with a SHA-256 checksum, holding:

- `irsty` (or `irsty.exe`)
- `irsty.1`, the man page
- `completions/`: `irsty.bash`, `_irsty` (zsh), `irsty.fish`, `_irsty.ps1` (PowerShell) and `irsty.elv` (Elvish)
- `README.md`, `LICENSE` and `CHANGELOG.md`

There are also installer scripts (`irsty-installer.sh` and `irsty-installer.ps1`, which put `irsty` in `~/.cargo/bin`), `sha256.sum` for every file, and the source tarball.

`dist plan` lists all of this without building anything.

## Man page and completions

`irsty --man` prints the man page, and `irsty --completions <bash|zsh|fish|powershell|elvish>` prints completions. Both are generated from the command-line definition (`crates/irsty/src/assets.rs`), so they always match the flags. Copies are kept in `assets/` for packagers, so building from source never needs a working `irsty` first. A test fails if they are out of date; `mise run assets` regenerates them.

| File | Install as |
|---|---|
| `assets/man/irsty.1` | `man1/irsty.1` |
| `assets/completions/irsty.bash` | `bash-completion/completions/irsty` |
| `assets/completions/_irsty` | `zsh/site-functions/_irsty` |
| `assets/completions/irsty.fish` | `fish/vendor_completions.d/irsty.fish` |

## Releasing

Releases are cut by pushing a version tag: the `Release` workflow (`.github/workflows/release.yml`, generated by dist) builds every archive and creates the GitHub release. On pull requests the same workflow only runs `dist plan`, as a check. When it succeeds for a tag, the `Publish crates` workflow (`.github/workflows/publish-crates.yml`) publishes the four crates to crates.io (see [The crates](#the-crates)).

1. Start from an up-to-date `main`, on a release branch.
2. Set `version` in `[workspace.package]` in `Cargo.toml` (and the matching `version` of each crate in `[workspace.dependencies]`).
3. Move the `[Unreleased]` section of `CHANGELOG.md` under the new version and date, and add the version's link at the bottom.
4. Set `MAN_DATE` in `crates/irsty/src/assets.rs` to the release date, then `mise run assets`.
5. `./scripts/gate.sh`, then `mise exec -- dist plan` to check the archives, and `cargo package --workspace` to check the crates build from what would be published (it resolves the unpublished crates locally).
6. Merge, then tag the merge commit on `main` and push the tag: `git tag v0.2.0 && git push origin v0.2.0`. Wait for the `Release` workflow, then `Publish crates` (`gh run watch`). Published versions can be yanked but never deleted.

dist itself is pinned in `mise.toml`. After changing `dist-workspace.toml` (or upgrading dist), run `mise exec -- dist generate` to regenerate the workflow; never edit `release.yml` by hand, or the check fails.

## The crates

`cargo install irsty` needs all four on crates.io, because `irsty` depends on the others. `irsty-core` and `irsty-tui` are Irsty's internals: their descriptions and docs say they make no API stability promise and that their versions move with the app. `irsty-proto` stands on its own as a sans-IO IRC library. Each crate carries a copy of `LICENSE` (a test checks the copies match), as cargo packages only what is in the crate's directory.

`Publish crates` runs after a successful `Release` run for a pushed tag. Before anything else it checks, and stops if any check fails, that the tag is a release version (`vX.Y.Z`; prereleases aren't published), that it points at the commit that was built, that the commit is on `main`, and that it matches the version in `Cargo.toml`. Then it runs `cargo publish --workspace`, which publishes the crates in dependency order and waits for each to appear before the next. Its job runs in the `crates-io` environment, which should require your approval (a required reviewer), so nothing reaches crates.io without a click. Don't rely on the environment's deployment branch rules: a `workflow_run` job always runs on `main`. It authenticates with [trusted publishing](https://crates.io/docs/trusted-publishing): GitHub's OIDC token is exchanged for a short-lived crates.io token, so no long-lived secret is stored.

Trusted publishing can only be set up for a crate that already exists, so the first release needs a token, once:

1. On crates.io, create an API token with the `publish-new` and `publish-update` scopes, limited to the `irsty*` crates and expiring in a few days.
2. In the repository settings, create the `crates-io` environment (Settings, Environments), add yourself as a required reviewer, and add the token as its `CARGO_REGISTRY_TOKEN` secret. Also add a tag ruleset (Settings, Rules) that lets only you create, move or delete `v*` tags. While the secret is set, the workflow uses it instead of trusted publishing.
3. Push the tag. Once the crates are published, add a trusted publisher to each of the four crates on crates.io (the crate's Settings, Trusted Publishing): owner `gawbul`, repository `irsty`, workflow `publish-crates.yml`, environment `crates-io`.
4. Delete the `CARGO_REGISTRY_TOKEN` secret and revoke the token. Optionally, turn on "trusted publishing only" for each crate.

If a run fails part-way, the crates already published stay published, and rerunning fails on them. Publish the rest by hand in order (`cargo publish -p irsty-core`, then `irsty-tui` and `irsty`).

## The project site

`book.toml` builds the site from `docs/`, with `docs/SUMMARY.md` as its table of contents and `docs/introduction.md` as its front page; a page in the summary that doesn't exist fails the build. `mise run book` serves it locally. The `Pages` workflow (`.github/workflows/pages.yml`) builds it on every pull request, as a check, and deploys it on every push to `main`. Pages must be set to deploy from "GitHub Actions" in the repository settings (once). Links from the docs to files outside `docs/` must be full GitHub URLs, as only `docs/` is in the site.

## Distribution packages

`packaging/` has starting points for three package managers. Each builds from a release's source tarball, installs the binary, the man page and the bash, zsh and fish completions, and needs a release tag to point at. Building needs Rust and a C and C++ compiler (for the bundled SQLite and Luau); there are no other system libraries to link.

| Package manager | Template | Status |
|---|---|---|
| Homebrew | `packaging/homebrew/irsty.rb` | Passes `brew style`; not yet installed from a tap. Put it in a tap (such as `gawbul/homebrew-tap`) as `Formula/irsty.rb`, set `url` and `sha256` for the release, and `brew install gawbul/tap/irsty`. Its test checks `--version` and that `--print-default-config` passes `--check-config`. |
| AUR (Arch Linux) | `packaging/aur/PKGBUILD` | Untested (no Arch machine here). Set `pkgver`, run `updpkgsums`, check with `namcap`, and publish to the AUR as `irsty`. It runs the `irsty-proto` tests, which need no network. |
| Nix | `packaging/nix/package.nix` | Untested (no Nix here). Use with `callPackage`; build once with the fake hashes and copy the real ones from the error. |

The full test suite starts mock servers on localhost, which some build sandboxes forbid, so the templates run the protocol tests only.
