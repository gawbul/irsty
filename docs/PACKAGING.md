# Packaging and releases

Irsty is released as archives on GitHub, built by [dist](https://opensource.axo.dev/cargo-dist/), and as crates on [crates.io](https://crates.io/crates/irsty), so `cargo install irsty` works. The project site is built from these docs by mdBook and deployed to GitHub Pages.

## What a release contains

For each of `aarch64-apple-darwin`, `x86_64-apple-darwin`, `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu` and `x86_64-pc-windows-msvc`, an archive (`.tar.xz`, or `.zip` on Windows) with a SHA-256 checksum, holding:

- `irsty` (or `irsty.exe`)
- `irsty.1`, the man page
- `completions/`: `irsty.bash`, `_irsty` (zsh), `irsty.fish`, `_irsty.ps1` (PowerShell) and `irsty.elv` (Elvish)
- `README.md`, `LICENSE` and `CHANGELOG.md`

There are also installer scripts (`irsty-installer.sh` and `irsty-installer.ps1`, which put `irsty` in `~/.cargo/bin`), a Homebrew formula (`irsty.rb`), `sha256.sum` for every file, and the source tarball.

`dist plan` lists all of this without building anything.

## Man page and completions

`irsty --man` prints the man page, and `irsty --completions <bash|zsh|fish|powershell|elvish>` prints completions. Both are generated from the command-line definition (`crates/irsty/src/assets.rs`), so they always match the flags. Copies are kept in `assets/` for packagers, so building from source never needs a working `irsty` first. A test fails if they are out of date; `mise run assets` regenerates them.

| File | Install as |
|---|---|
| `assets/man/irsty.1` | `man1/irsty.1` |
| `assets/completions/irsty.bash` | `bash-completion/completions/irsty` |
| `assets/completions/_irsty` | `zsh/site-functions/_irsty` |
| `assets/completions/irsty.fish` | `fish/vendor_completions.d/irsty.fish` |

## Releasing

Releases are cut by pushing a version tag: the `Release` workflow (`.github/workflows/release.yml`, generated by dist) builds every archive and creates the GitHub release. On pull requests the same workflow only runs `dist plan`, as a check. When it succeeds for a tag, the `Publish crates` workflow (`.github/workflows/publish-crates.yml`) publishes the four crates to crates.io (see [The crates](#the-crates)).

1. Start from an up-to-date `main`, on a release branch.
2. Set `version` in `[workspace.package]` in `Cargo.toml` (and the matching `version` of each crate in `[workspace.dependencies]`).
3. Move the `[Unreleased]` section of `CHANGELOG.md` under the new version and date, and add the version's link at the bottom.
4. Set `MAN_DATE` in `crates/irsty/src/assets.rs` to the release date, then `mise run assets`.
5. `./scripts/gate.sh`, then `mise exec -- dist plan` to check the archives, and `cargo package --workspace` to check the crates build from what would be published (it resolves the unpublished crates locally).
6. Merge, then tag the merge commit on `main` and push the tag: `git tag v0.2.0 && git push origin v0.2.0`. Wait for the `Release` workflow, then `Publish crates` (`gh run watch`). Published versions can be yanked but never deleted.

dist itself is pinned in `mise.toml`. After changing `dist-workspace.toml` (or upgrading dist), run `mise exec -- dist generate` to regenerate the workflow; never edit `release.yml` by hand, or the check fails. The actions in `release.yml` are pinned to commits by `[dist.github-action-commits]` in `dist-workspace.toml`; when updating the other workflows' pins, update these too ([VERSIONS](VERSIONS.md#github-actions-checked-2026-11-07) lists them). Upgrading dist can change which actions it uses, so check the regenerated workflow for any `@v` left unpinned.

## The crates

`cargo install irsty` needs all four on crates.io, because `irsty` depends on the others. `irsty-core` and `irsty-tui` are Irsty's internals: their descriptions and docs say they make no API stability promise and that their versions move with the app. `irsty-proto` stands on its own as a sans-IO IRC library. Each crate carries a copy of `LICENSE` (a test checks the copies match), as cargo packages only what is in the crate's directory.

`Publish crates` runs after a successful `Release` run for a pushed tag. Before anything else it checks, and stops if any check fails, that the tag is a release version (`vX.Y.Z`; prereleases aren't published), that it points at the commit that was built, that the commit is on `main`, and that it matches the version in `Cargo.toml`. Then it runs `cargo publish --workspace`, which publishes the crates in dependency order and waits for each to appear before the next. Its job runs in the `crates-io` environment, which should require your approval (a required reviewer), so nothing reaches crates.io without a click. Don't rely on the environment's deployment branch rules: a `workflow_run` job always runs on `main`. It authenticates with [trusted publishing](https://crates.io/docs/trusted-publishing): GitHub's OIDC token is exchanged for a short-lived crates.io token, so no long-lived secret is stored.

Trusted publishing can only be set up for a crate that already exists, so the first release needs a token, once:

1. On crates.io, create an API token with the `publish-new` and `publish-update` scopes, limited to the `irsty*` crates and expiring in a few days.
2. In the repository settings, create the `crates-io` environment (Settings, Environments), add yourself as a required reviewer, and add the token as its `CARGO_REGISTRY_TOKEN` secret. Also add a tag ruleset (Settings, Rules) for all tags, not just `v*`, that lets only you create, move or delete them: the `Release` trigger matches any tag with a version in it (such as `x1.2.3`), and its Homebrew job runs before any of the checks in `Publish crates`. While the secret is set, the workflow uses it instead of trusted publishing.
3. Push the tag. Once the crates are published, add a trusted publisher to each of the four crates on crates.io (the crate's Settings, Trusted Publishing): owner `gawbul`, repository `irsty`, workflow `publish-crates.yml`, environment `crates-io`.
4. Delete the `CARGO_REGISTRY_TOKEN` secret and revoke the token. Optionally, turn on "trusted publishing only" for each crate.

If a run fails part-way, the crates already published stay published, and rerunning fails on them. Publish the rest by hand in order (`cargo publish -p irsty-core`, then `irsty-tui` and `irsty`).

## The project site

`book.toml` builds the site from `docs/`, with `docs/SUMMARY.md` as its table of contents and `docs/introduction.md` as its front page; a page in the summary that doesn't exist fails the build. `mise run book` serves it locally. The `Pages` workflow (`.github/workflows/pages.yml`) builds it on every pull request, as a check, and deploys it on every push to `main`. Pages must be set to deploy from "GitHub Actions" in the repository settings (once). Links from the docs to files outside `docs/` must be full GitHub URLs, as only `docs/` is in the site.

## Homebrew

dist builds a Homebrew formula with each release and pushes it to the tap [`gawbul/homebrew-tap`](https://github.com/gawbul/homebrew-tap) as `Formula/irsty.rb` (the `publish-homebrew-formula` job in `release.yml`), so `brew install gawbul/tap/irsty` installs the prebuilt binary for macOS or Linux, on Apple silicon, Intel or ARM. The job pushes with the `HOMEBREW_TAP_TOKEN` secret: a fine-grained token with read and write access to the tap's contents and nothing else. It runs after the archives are uploaded and before the GitHub release is created, so a failed push stops the release (and so the crates) too; prereleases are skipped.

The formula installs only the binary in `bin`; the man page and completions from the archive go in `$(brew --prefix)/share/irsty` (Homebrew's `pkgshare`), where `man` and the shells don't look. `man "$(brew --prefix)/share/irsty/irsty.1"` reads the man page, and `irsty --completions <shell>` prints completions to load from a shell's startup file. dist's tap commits are authored by "axo bot", which dist doesn't let us change. dist can't run the job in an environment, so `HOMEBREW_TAP_TOKEN` is a repository secret; the tag ruleset (see [The crates](#the-crates)) is what stops anyone else starting a release, and the token can write only to the tap.

## Scoop (Windows)

`scoop bucket add gawbul https://github.com/gawbul/scoop-bucket`, then `scoop install gawbul/irsty`, installs the Windows archive. dist has no Scoop installer, so the `Publish Scoop manifest` workflow (`.github/workflows/publish-scoop.yml`) does it: after a successful `Release` run it makes the same checks as `Publish crates` (`scripts/check-release-tag.sh`), writes `irsty.json` with `scripts/scoop-manifest.sh` from the archive's published SHA-256, and pushes it to the bucket as `bucket/irsty.json`. It pushes with `SCOOP_BUCKET_TOKEN`, a fine-grained token with read and write access to the bucket's contents and nothing else. The job runs in the `scoop-bucket` environment: keep the token there, not as a repository secret, and require yourself as a reviewer, so only an approved run can read it (unlike `HOMEBREW_TAP_TOKEN`, as dist's Homebrew job can't use an environment). The manifest has no `checkver` or `autoupdate`, because the workflow is what updates it. To publish or repair the manifest for an existing release, run the workflow by hand: `gh workflow run publish-scoop.yml -f tag=v0.1.0` (or Actions, Publish Scoop manifest, Run workflow). It makes the same checks and needs the same approval. Its notes say where the man page and completions are, and how to load PowerShell completions. The binary isn't code-signed, so SmartScreen may warn the first time it runs.

## Nix

`flake.nix` makes the repository a Nix flake, for Linux and macOS on x86_64 and ARM:

```sh
nix run github:gawbul/irsty            # run the latest main
nix profile install github:gawbul/irsty
```

From the next release on, a tag pins a release (`github:gawbul/irsty/v0.2.0`); `v0.1.0` predates the flake. Nothing is published for Nix, so there is no workflow to run: the flake is read from the repository.

It builds `packaging/nix/package.nix` from the checkout and its `Cargo.lock`, so it has no hashes to update; the only thing to maintain is `flake.lock`, which pins nixpkgs (`nix flake update`, then check it builds). There is no binary cache, so Nix compiles Irsty, which takes a few minutes. The build runs the protocol tests and checks `irsty --version`, and installs the man page and the bash, zsh and fish completions.

`packaging/nix/package.nix` is written as a nixpkgs package (`pkgs/by-name/ir/irsty/package.nix`), with the hashes for the current release, ready to submit to nixpkgs. That means a pull request to NixOS/nixpkgs, adding the package and, in a separate commit, its maintainer to `maintainers/maintainer-list.nix`; after that, nixpkgs' update bot proposes each new release. For a new release, set `version`, set both hashes to `lib.fakeHash`, build, and copy the hashes Nix reports.

## AUR (Arch Linux)

`packaging/aur/` holds a `PKGBUILD` and its `.SRCINFO`, ready to publish as `irsty`. It builds the release named by `pkgver` from its source tarball (checked by SHA-256), runs the protocol tests, and installs the binary, the man page, the bash, zsh and fish completions, and the licence. Building needs Rust and a C and C++ compiler (for the bundled SQLite and Luau); there are no other system libraries to link.

It isn't on the AUR yet: AUR account registration is paused. Once you have an account with an SSH key, publishing is: clone `ssh://aur@aur.archlinux.org/irsty.git`, copy in `PKGBUILD` and `.SRCINFO`, commit and push. For a new release, set `pkgver` (and `pkgrel=1`), run `updpkgsums`, and `makepkg --printsrcinfo > .SRCINFO`.

`scripts/aur.sh` checks it inside Arch Linux: that `.SRCINFO` is current, `namcap` on the `PKGBUILD` and the package, and `makepkg` itself. `mise run packaging:aur` runs it in Docker (emulated on ARM Macs, so slowly).

## Testing the packages

The `Packaging` workflow (`.github/workflows/packaging.yml`) runs when `packaging/`, the flake, `Cargo.lock` or the packaging scripts change:

- the AUR package in an `archlinux` container (`scripts/aur.sh`);
- `nix flake check` and `nix run . -- --version` on Linux x86_64, Linux ARM and macOS;
- on Windows, the Scoop manifest for the latest release, installed with Scoop and run.

`mise run packaging:aur` and `mise run packaging:nix` run the first two locally in Docker. The full test suite starts mock servers on localhost, which build sandboxes forbid, so the packages run the protocol tests only.
